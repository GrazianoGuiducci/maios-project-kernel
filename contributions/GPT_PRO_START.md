# GPT Pro contribution start

This packet opens one contribution cycle with GPT Pro or another frontier
model. Give the model the public repository URL after the revision containing
this file is available, or upload the listed files directly.

Before using a return, preserve the exact commit or uploaded source bundle it
refers to. A newer local source can change the meaning of the review.

- `AGENTS.md`
- `knowledge/KERNEL.md`
- `research/AI_KERNEL_PAPER_FIELD.md`

## Copy/paste prompt

```text
You are participating in the public MAIOS Project Kernel competence field as
an independent high-capacity contributor.

Speaker and authority:
This packet was prepared by the repository's local AI collaborator from the
operator's direction. You are not the operator and your output does not grant
merge, package, release, installation or publication authority.

What we want to happen:
Understand the Kernel from the supplied public sources, then expose one
high-leverage relation that can make this repository's knowledge, paper field,
competence system or coder experience more capable. Let the contribution take
the smallest complete form that can change a later result: a competence,
method, source correction, research delta, falsifier, test or patch.

How to understand the field:
KA keeps the possibility field open. FDLA preserves causal coherence while the
movement occurs. Meta_Skill composes, forms and evolves the competence that can
carry a reusable difference. Treat these as one operating relation, not as a
checklist or as names that prove the Kernel works.

Desired resultant:
One source-bound, patch-ready contribution that is useful to a coder who clones
the repository and to later non-identical work. If the strongest result is an
unresolved tension or falsifier, preserve it instead of forcing a feature.

Validity conditions:
- state the commit or exact files you could actually inspect;
- distinguish repository fact, interpretation, hypothesis and proposal;
- do not infer private topology, runtime behavior or evidence outside the
  supplied public source;
- keep repository contribution distinct from package inclusion and release;
- use the contribution template so the result can be reintegrated locally.

First expand the field:
Identify hidden possibilities, tensions, competing explanations and missing
relations that the current public form makes reachable.

Then form the contribution:
Select the one relation with the strongest capacity to change a later result.
Return exact target files, replacement text or a unified diff when possible,
plus the test, falsifier or observation that would expose its value.

Expected output:
1. Source revision and coverage.
2. Your concise understanding of the Kernel's constitutive relation.
3. The selected possibility or tension and why it matters.
4. A completed Competence Contribution body.
5. Patch-ready files or diff.
6. Acceptance evidence, invalidator and first reentry circumstance.
7. What remains unchanged, especially package and release effects.
8. Questions whose answers could materially change the contribution.
```

## Local return

Bring the complete response back to the local repository owner. Each
substantial proposal will be classified as `accept`, `adapt`, `defer`,
`reject`, or `needs_verification`, then any accepted portable difference will
be applied to its closest public owner and validated there.

The first return tests whether this public contribution competence changes an
actual subsequent movement. Until that use occurs, the path is represented and
available; its assimilation remains unobserved.
