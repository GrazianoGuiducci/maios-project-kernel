# Repository continuity in the receiving system

Keep source knowledge and actual shared state intelligible. A saved file, local commit, tracking reference, authenticated remote revision, integrated branch and deployed product are different facts. Determine which one matters to the current result.

## Understand the existing work

Read the selected repository's own instructions and the present operator relation. Identify current branch and revision, pending changes, concurrent work and the source that should receive the result. A familiar directory name or stale tracking ref does not establish that identity.

Classify useful accumulated work by its meaning before selecting changes. Old or uncommitted content can still contain valid knowledge. Keep unrelated work outside the selected change; do not reset, force-push or make the worktree look clean by discarding it.

## Make the appropriate continuity real

If the selected outcome includes sharing source work, inspect the exact change, preserve independently produced contributions, record a coherent commit and use the actual authorized remote route. Verify the intended remote revision before calling it shared. If publication is not authorized, retain the prepared work and describe the unperformed effect without treating comprehension as blocked.

A work branch can make a contribution reachable without merging it into the canonical branch. Reconcile divergence according to the actual source relationships. A newer commit does not win automatically, and a merge with no textual conflicts does not establish semantic compatibility.

Do not transport a previous operator's standing permission to commit or push. Authorization belongs to this receiving environment and selected work. Source publication does not imply a release, deployment, account change or update to another host.

## Example of a consequential distinction

An agent updates a method locally and tells another instance to use it. The second instance can read only the remote repository, which still contains the earlier body. The method exists but the intended continuation is incomplete. The correction may be an authorized source checkpoint or a clear handoff of the exact prepared artifact, not another rewrite of the method.

A release can remain valid while later documentation changes the repository's source identity. Follow the product's real build relation when derived metadata must be refreshed; do not retroactively claim that old release tests were run on the new source.

## Preserve and learn

Keep enough current state to recover the changed knowledge, its reason, exact branch/revision and any still-local contribution. Reach deeper evidence when a conflict or recovery makes it useful. Do not add a Git ceremony to greetings, read-only inquiry or every small edit.

If a later case exposes a missed source boundary, hidden work or unnecessary publication, teach the causal difference to this competence and its actual consumers. Shared availability is not proof that another instance has acquired, understood or used the result.
