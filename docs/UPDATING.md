# Update a project that has already learned

[Italiano](UPDATING.it.md) · [installation/recovery](INSTALLATION.md) ·
[owning update method](../kernel/UPDATE_CONTINUITY.md)

A new package can improve a project without replacing what that project has
learned. This guide serves the operator and their coder when an update is
actually useful. It is not an automatic updater or an instruction to install
every newer source. Ordinary work can continue while an update remains a possibility.

## Establish the actual receiving project

Read current intent, the acting competence's guide and the files used now.
Retain local methods, configuration, learning/operating state, native entries,
sources and current work. Keep a recoverable copy of the affected before-images;
a Git commit is useful only when it includes the material that must be recovered.
Do not publish private content merely to create a backup.

Recover the exact installed artifact and the original installation receipt
when available. `update_baseline` records distributed identity, file digests
and source/destination relations; it does not mean that every living local file
still has those bytes. The installed installer's `verify` distinguishes an
internally consistent historical baseline from present `target_evolved` files.
An absent base limits the comparison; do not reconstruct it from a version name.

## Understand the change before selecting its application

Keep the proposed package/source outside the existing target. Compare the
distributed base, current local body and new upstream body through the owner
that understands the method. A newer date does not supersede useful local
knowledge. The result can be no change, a selective adaptation or a broader
update; preserve its reasons rather than forcing one universal merge policy.

Follow required references, tools and native entries as well as the changed
file. One body can refer to knowledge absent in the receiving project. Resolve
actual state-contract differences before applying a structural change; 5.5.0
retains the 5.1.0 contracts, but the particular local project may have evolved.
Do not copy a newly installed target's empty state over living state.

## Carry the selected local change and recovery

Prepare the exact changed paths, intended meaning, preserved local contributions
and recovery relation. Recheck affected content at the moment of replacement
so another writer's work is retained. Apply only the selected owner-native
adaptation. A semantic conflict needs understanding, not a forced overwrite.

Follow the result into the actual body, references and host entry used next.
Preserve the source identity, adaptation, affected paths and remaining work
in the existing task/competence guide. Test changed mechanics and useful
continuation in proportion to the actual change. An upstream body and a local
recomposition may legitimately have different bytes.

The historical installation receipt is derived from its original install plan.
The current installer has no operation to advance only part of that baseline.
Keep selected knowledge integration as attributable local evolution; do not
edit the old receipt to make it claim a new installation. A partially integrated
kernel retains that scope. Managed CURRENT_STATE/PROJECT_BRIEF projections
are regenerated from configuration: durable methods/reasons also belong in
their living owners, with the supported configuration update for managed facts.

## Installer boundaries

Preview/apply installs an exact artifact and refuses divergent file conflicts.
Reapplying that same unchanged artifact can be idempotent; applying another
version is not an in-place migration. If a fresh installation helps comparison,
use a separate target and keep the old target intact. Do not uninstall an
evolved project merely to make a new install plan pass.

Uninstall/recovery removes only material owned by the qualified installation
and still matching its required identity. Locally evolved or uncertain files
need preservation and inspection. A new empty installation is not a substitute
for the original receipt or its recovery history.

You can ask the coder:

```text
Compare this project's installed base, local learning and the proposed MPK
version. Show the useful differences, required references, exact receiving
paths and recovery. Preserve my current knowledge and state. Prepare a
concrete selective integration; do not force an installer overwrite.
```

The [compatibility guide](COMPATIBILITY.md) and current sources determine the
actual contracts. Installation, method exposure, use and later assimilation
remain separate observations; an artifact version alone does not prove them.
