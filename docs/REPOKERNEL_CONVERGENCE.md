# RepoKernel convergence into MAIOS Project Kernel 3.0

RepoKernel and the autonomous MAIOS Project Kernel have different roles.
RepoKernel compiles a neutral project relation. This repository owns the
self-configuring product, its installation, its living semantic entry and its
continued evolution. Version 3.0 assimilates the useful generated functions
without embedding RepoKernel or creating a second Kernel owner.

## Retained generated functions

- `PROJECT_META_FACULTY.json` enters as an open 18-family coverage map. It
  helps the permanent system competence recognize relevant relations; a family
  name never forces routing or grants effect authority.
- RepoKernel's generated Project Entity Profile enters only through an
  owner-native translation. It preserves role, capability requirements,
  source catalogues and completion relation while replacing the fixed
  primary/support palette with selection by material relation and observed
  delta.
- Environment readiness becomes part of first integration and host adaptation:
  a capable coder or harness, model access and Python are required; Git and a
  shared repository are recommended; remote infrastructure remains situated.

## Existing owner-native equivalents

The remaining generated organs are not copied because the autonomous package
already owns their functions:

| RepoKernel projection | MAIOS 3.0 owner-native relation |
| --- | --- |
| clarity and delta notes | `CURRENT_STATE.md`, architecture and resultant readback |
| entity bootstrap and first packet | `START_HERE.md` plus new/existing-project startup competences |
| capability binding and skills registry | `FACULTY_FIELD.json`, competence index, adapters and inventory |
| host attestation | `HOST_STATE.json` and host-adaptation competence |
| evidence, manifest and source atlas | package receipts, manifest, inventory and source manifest |
| operations entry | `maios.py`, project runtime and operating state |
| generated semantic skill | `SYSTEM_KERNEL.md` plus the permanent `maios-project-system` owner |
| current-state and instruction deltas | existing owner-native state and `AGENTS.md` surfaces |

A static problem/possibility seed is absent from the direct package because
its project context is intentionally deferred to the first operator relation.
The Form-generated package will supply that context before entry while
converging on the same installed Kernel relation.

## Resulting product boundary

The 3.0 package remains independently installable and self-configuring.
RepoKernel source, staging paths, runtime and fixed selection topology do not
enter its bytes. The later Form package may differ in accepted configuration
and startup state, but not in the semantic Kernel family it installs.

## Family update bridge

`kernel/PROJECT_KERNEL_FAMILY_CONTRACT.json` is the product lock of the small
transfer contract maintained by the Project Kernel family competence. It
records only reusable result-changing invariants and the
autonomous entry condition. The deterministic build projects it to
`payload/.maios/kernel/PROJECT_KERNEL_FAMILY_CONTRACT.json`.

When the autonomous Kernel changes in a way that must also change the Form
product, the family competence synchronizes the two product locks, rebuilds
both products and compares their generated family signatures. Identical locks
do not prove aligned behavior; profiles, functional coverage, environment
readiness and lane-specific entry state must also converge.
