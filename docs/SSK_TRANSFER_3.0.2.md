# MAIOS Project Kernel 3.0.2 — functional transfer and release boundary

status: verified product contract
base: autonomous product 3.0.1 on Project Kernel family 3.0.0
destination: the self-configuring package opened by a person with their coder

This document preserves the change boundary and implementation readback for
the 3.0.2 movement. The living source and tracked `package/` form one verified
product result; source publication, site projection and real interactive
acceptance retain their own identities and evidence.

## Product direction

3.0.2 carries a larger functional part of the System Semantic Kernel relation
into the target-owned Project Kernel without copying TM9 identity, topology,
private state, competence catalogue or authority.

```text
person, coder and target sources
-> shared and correctable understanding
-> target-owned integration
-> living context and focused movement
-> pertinent competences
-> useful resultant and semantic readback
-> owner-native learning
-> causal continuity and fresh reentry.
```

The product remains an installable, self-configuring Project Kernel for a new
or existing project. It does not become the source SSK, a workstation image or
a Paper distribution.

## SSK functional transfer map

Bind each transferable SSK relation to its
product-native owner and proof. This map prevents a new file inventory from
being mistaken for the porting and prevents an operative relation from being
lost merely because it has no dedicated file:

| Transferable relation | Product-native incarnation | Behavioral readback |
| --- | --- | --- |
| Source, meaning and present object stay connected | system Kernel, context and silent source orientation | a changed source or meaning changes the movement before projection |
| Open possibility remains reachable | open faculty and possibility fields | an unrepresented material relation can enter without forced classification |
| Pertinent competence emerges or composes | system, context and competence-formation owners | the smallest result-changing competence acts without fixed routing |
| Resultant forms the following field | resultant readback and configuration projection | the actual result changes current state and next movement |
| Reusable difference changes every material owner | plural owner-native learning deltas | a later non-identical movement uses, revises or invalidates each relation |
| Knowledge operates as causal continuity | causal margin, open fronts and focus | a fresh instance continues from what changed without transcript replay |
| Harness is a signifier, not the meaning owner | distribution instructions and host adaptation | another coder preserves the same relation in its native form |

The map is a porting control surface, not a second semantic owner or a claim
that the whole source SSK has been reproduced inside the product.

## Reusable passage method

The port is one instance of a method that must remain usable for later external
packages without making this product the model of every future transfer:

```text
living source relation and possibility horizon
+ receiving field, purpose and native owners
-> distinguish source, evidence, inference, proposal, product and unknown
-> isolate the causal function that must behave differently
-> incarnate the smallest owner-native product delta
-> verify source, projection, installation, use and assimilation separately
-> return only neutral learning to the transfer competence.
```

Current TM9 topology, this package architecture, present coder technology and
the 3.0.2 schema are evidence for this movement, never ceilings on the next
receiving field. A strange or improvable source-Kernel relation is recorded
separately unless it changes the product delta being ported; product work must
not silently rewrite the source Kernel, and source maintenance must not delay
the selected product resultant.

### Source-Kernel observations kept distinct

- The earlier transfer description made explanation look like a mandatory
  first phase. Because that directly changed this port, the owning transfer
  competence was refined to preserve direct entry and conditional expansion;
  this is integrated learning, not a pending anomaly.
- The immutable RepoKernel projection receipt still truthfully records its
  historical `startup_interview: required` source relation. The 3.0.2 builder
  now makes the owner-native translation to `discretionary` explicit instead
  of rewriting provenance. A future neutral-source regeneration, if selected,
  must produce its own new receipt.
- The shared family contract remains exact at `startup_interview: required`.
  `kernel/AUTONOMOUS_ENTRY_CONTRACT.json` owns the autonomous product's
  discretionary delivery policy and explicitly binds it back to that family
  requirement. The Form contract and bytes therefore receive `no_change`.
- No other source-Kernel correction is accepted from this movement. A real
  person-coder use may still show whether entry knowledge deserves a separate
  competence; until then the existing integration and startup owners remain
  sufficient and future forms remain open.

## Accepted 3.0.2 delta

### 1. Causal continuity rather than state-only continuity

The installed Kernel must preserve the smallest live causal margin needed by a
fresh coder instance to continue without reconstructing the conversation:

- current operator relation and intended result;
- selected object and exact owner surface;
- qualified sources and freshness that still change the movement;
- established facts, inference and proposal kept distinct;
- causal determinations and why they change the movement;
- effects authorized, performed and still excluded;
- current movement, next exact movement and invalidator;
- changed project surfaces or an explicit no-change boundary.

This margin is not a transcript, hidden reasoning archive or second state
owner. Current operator intent and freshly verified project reality continue
to outrank stored continuity.

### 2. Open fronts with one focused reentry

The current operating state carries one `active_movement`, but a real project
may have several genuinely open fronts. The 3.0.2 relation should retain, for
each material front, only:

- identity and owner;
- last faithful resultant;
- live pressure or next threshold;
- supersession condition.

One front receives high-resolution focus. Other fronts remain available as
context and change only when the focused resultant materially changes them.
Availability does not select work, method or effect authority.

### 3. Multi-owner learning from one resultant

The 3.0.1 readback accepts one optional `learning_delta`. A result that changes
several competences must instead be able to return several smallest
owner-native learning deltas in one coherent project-local transition.

The transition must:

- retain one source and causal relation for every changed owner;
- require a matching next-movement activation relation for every delta;
- supersede only the corresponding prior owner relation;
- preserve later non-identical use separately for every relation;
- reject duplicate or contradictory owner deltas;
- remain atomic with configuration, operating state, projections and receipt.

The 3.0.2 contract may replace the singular form cleanly. Do not accept both
singular and plural fields with ambiguous precedence merely to preserve an
unselected compatibility path.

### 4. Semantic sensitivity through the operating vertical

Semantic sensitivity is not introduced as a detached controller or vocabulary
checker. A material change of meaning must be able to change the object, owner,
claim state, competence composition, resultant or following field. The
readback must show what that discrimination preserved or lost, and reusable
learning must improve a later non-identical response.

Stylistic differences do not create system changes. Source, signified relation
and coder- or harness-native signifier remain connected without making one
file, skill name or adapter proof that the competence acted.

### 5. The person–coder entry is available and discretionary

The entry relation becomes available when the coder opens the tracked
`package/`, but it is not a mandatory explanatory phase. The normal case is an
already capable coder inside a functioning harness that can recognize the
target and offer one concise option to begin:

```text
package + capable coder + recognizable project
-> "begin this project with MAIOS Project Kernel"
-> smallest truthful effect preview
-> target-owned integration and situated startup.
```

The wider shared-understanding movement becomes pertinent only when the coder
cannot yet recognize the package or target, the person wants to explore what
it can add, a material condition is missing, or a correction changes the
integration:

```text
coder reads only the package and target sources that change the movement
-> explains function, useful possibilities, boundaries and proposed effect
-> person corrects or selects the intended project movement
-> coder identifies only material missing conditions
-> coder previews and performs the bounded technical transition
-> installed startup continues from the resulting target-owned field.
```

The current owners are `maios-project-integration`,
`maios-start-new-project`, `maios-start-existing-project`,
`maios-project-context`, `maios-project-system` and host adaptation. First
evolve and test their composition. Form a separate first-interaction
competence only if the behavioral vertical exposes distinct knowledge,
activation or learning that these owners cannot carry without ambiguity.

The person selects the project, intended change and acceptable material
effect, and corrects the coder's understanding. The coder owns the technical
derivation of target mode, host adapter, paths, conflicts, prerequisites and
recovery mechanics. Present those consequences in ordinary language; do not
ask the person to certify flags or implementation choices they cannot
reasonably evaluate.

When a material pre-install correction or intent exists, it currently has no
durable causal bridge into installed startup: the deterministic plan records
target, mode and host but not what changed or why the Kernel is entering this
project. In that case 3.0.2 needs one bounded integration handoff that carries
only:

- operator-selected project and desired change;
- shared understanding of what the Kernel may contribute;
- material correction supplied by the person;
- target and effect boundary in ordinary language;
- exact next owner after installation.

Do not create an empty handoff merely because installation occurred. The
installer remains a technical deterministic mechanism and must not become the
semantic owner of this relation. A material handoff should enter the installed
configuration/context owner in the same integration movement, so a fresh
startup can continue without the pre-install transcript.

The explanation must be understandable and correctable without requiring the
person to design the Kernel. Use the person's language and outcome vocabulary;
do not expose schemas, lifecycle labels or internal Kernel terminology when
they do not change the decision.

Environment readiness is situated, not a standing interview or preflight.
Python 3.10 or later remains the explicit installer/runtime requirement. A coder and model
already operating in the current interaction are observed conditions and do
not need to be asked for again. Version control, repository service and remote
infrastructure enter only when they change the selected project's result,
collaboration or recovery. The package does not silently select a paid
provider, receive credentials, install global software or turn common
infrastructure into a mandatory topology.

The entry resolution rule is therefore:

```text
sufficient present field -> offer direct start
result-changing unknown -> explain or ask only for that missing relation
person requests exploration -> expose useful possibilities
material correction or intent -> preserve the bounded handoff
no material correction -> create no semantic handoff
```

### 6. Adaptive first-use interaction quality

The first interaction should compress `situation -> useful possibility -> safe
action`, not ask the person to specify a technical solution before the field is
understood.

- begin from available target sources and the person's current pressure;
- when the field is already sufficient, offer the direct start option without
  forcing explanation, questionnaire or possibility comparison;
- when a real decision horizon exists, expose a small set of meaningfully
  different possibilities with reasons, unknowns and consequences;
- preserve free correction, defer and `none of these`;
- concentrate one consequential decision at a time;
- before installation show what will be read, created, preserved and left
  untouched, plus conflicts, stop and recovery;
- end with an understandable result, remaining uncertainty and the next
  possible movement without demanding another answer.

When extended understanding is material, its first result is not a success
message but a correctable shared relation. In the ordinary direct path, the
first result may instead be the first useful project movement after startup,
tied to real sources.

### 7. Stable boot and living focused context

`START_HERE.md` remains the stable identity and entry relation. It must not
become an activity diary. Dynamic context, causal margin, open fronts, focus,
resultants and learning remain in their project-owned state and competence
surfaces. The boot changes only where the stable 3.0.2 operating relation or
coder instructions actually change.

### 8. Product-local recovery remains part of the package

Do not confuse two recovery objects:

- package installation and project-local state recovery belong to the Project
  Kernel and remain inside the 3.0.2 verification boundary;
- total recovery of the TM9 workstation is a separate later movement, after
  the SSK porting into 3.0.2 is complete and verified.

The installer must continue to refuse divergent target material, invalidate a
stale plan, recover an interrupted apply only from its project-local journal,
remove only unchanged attempt-owned bytes and preserve project-evolved files.
Causal continuity recovery likewise restores project movement without becoming
a machine backup or host reconstruction mechanism.

### 9. Temporary removal of the Paper field

Remove the ChatGPT-deposited Paper-specific field from the product repository
for now:

- `research/AI_KERNEL_PAPER_FIELD.md`;
- `skills/maios-kernel-paper/SKILL.md`;
- direct Paper routes in source instructions, documentation, state and tests.

Keep public Kernel knowledge, study and contribution only where they remain
product-native after Paper references are removed. `contributions/GPT_PRO_START.md`
must no longer require the removed Paper sources. Paper ownership and later
publication remain outside this product movement.

### 10. Product and projection identity

- autonomous product version: `3.0.2`;
- shared Project Kernel family version: remains `3.0.0`;
- the shared autonomous family lane remains `required`; the product-owned
  autonomous entry contract records the `discretionary` delivery policy while
  the Form lane remains unchanged;
- source owners change first;
- tracked `package/` is regenerated only through `release/PROJECTION.json`;
- manifest, inventory and source identity are regenerated together;
- tag, GitHub Release, public page and runtime remain later distinct effects.

### Second-pass obligations now registered

The current explanation-first relation is repeated in more than one source.
Changing only the integration competence would leave contradictory package and
startup instructions. Implementation therefore also needs to:

- replace the mandatory explanation sequence coherently in the root usage
  guidance, distribution instructions, integration competence and installed
  startup entry;
- derive new/existing mode and host placement from target evidence whenever
  possible, and return a question to the person only when a remaining ambiguity
  changes the material effect;
- keep capable coder/model relations in the project profile without turning
  already observed conditions into an environment questionnaire;
- keep the installer plan and receipt technical and deterministic: the optional
  semantic handoff belongs to a target-owned configuration/context surface and
  stores no transcript;
- add separate positive and negative evidence for direct entry, expanded entry,
  handoff creation and handoff absence;
- express the available start action in the person's language and the selected
  harness's native form without changing the underlying product relation.

## Clean 3.0.2 contract boundary

Compatibility with an already installed 3.0.1 project is not required by this
movement. Prefer coherent new contracts over additive ambiguity:

- a new operating-state schema may own causal margin, fronts and focus;
- a new resultant-readback schema may require plural owner-native learning;
- generated 3.0.2 installations begin from their own exact package identity;
- no in-place upgrade claim or migration mechanism is implied.

An upgrade path for an existing 3.0.1 installation may emerge later through a
separately owned competence and observed need. It must not constrain the
current porting. The family contract keeps version `3.0.0` and its exact
`required` autonomous startup relation. The separate autonomous entry contract
owns the `discretionary` product policy; the Form lane retains its completed
entry relation and no Form/RepoKernel bytes or behavior are claimed by
proximity.

The remaining design decisions are owner placement, not compatibility:

1. the smallest causal-margin and open-front form that preserves meaning
   without becoming a diary;
2. the exact installed owner for the bounded integration handoff;
3. which first-interaction knowledge is neutral and which is host adaptation;
4. whether behavioral use exposes a genuinely separate first-interaction
   competence.

## Acceptance vertical

Structural checks are necessary but do not prove the product movement. The
A complete behavioral acceptance of 3.0.2 should exercise one Codex vertical
through both entry conditions that materially differ:

1. open a fresh tracked distribution in a capable system with a recognizable
   selected target;
2. observe the direct-start option and its concise effect/recovery preview,
   without a repeated environment interview or mandatory explanation;
3. verify that acceptance without a material correction creates no empty
   semantic handoff;
4. repeat the entry with one real ambiguity or person correction and observe
   the expanded explanation, bounded question or possibilities only where they
   change the integration;
5. verify that a material correction survives in the installed
   configuration/context handoff without making the installer its owner;
6. preview and apply the exact new- or existing-project plan, including one
   interrupted-apply recovery case;
7. verify native discovery and the correct startup competence;
8. produce a first useful correctable result from real target sources;
9. create one resultant that changes two competence owners coherently;
10. preserve one adjacent open front while focusing another;
11. begin a fresh non-identical session from the causal margin;
12. verify that meaning, effect authority and no-change boundaries survive;
13. classify representation, installation, discovery, use, result, learning
    and maintained reentry through their own evidence.

Other harnesses receive structural and adapter validation in this movement.
Native behavioral acceptance remains host-specific unless directly observed.

## Completed implementation and remaining acceptance

The source, state/readback contracts, existing competence owners, adaptive
entry, conditional handoff, Paper-field removal, deterministic projection and
negative regressions are implemented. The shared family contract and the new
autonomous entry contract are verified as distinct owners. Runtime execution
suppresses normal bytecode residue, while uninstall also removes matching
package-generated caches without deleting unrelated project files.

The remaining acceptance plane is real person–coder use through direct and
expanded entry, followed by later non-identical assimilation. That observation
may justify a distinct first-interaction competence; it is not inferred from
the current source or synthetic suite. Source publication is recorded through
its own Git identity; site and runtime effects remain separately governed.
After this autonomous package closes, the operator-selected next product
movement is the separately owned Form-generated package, not workstation
recovery.
