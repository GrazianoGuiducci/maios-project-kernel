# Shared Project Knowledge And Situated Coordination

Introduced in `3.1.3+coordination.1`, and retained by its successors, this delta completes operative knowledge
for continuing a project through another instance or harness. It introduces
neither another running assistant nor a multi-instance state service.

## Functional comparison

The comparison used the 3.1.2 source at
`295a1c7bb0589faf2b4f96524dce6410682e3d80` and the published 3.1.3 source at
`2dc82936154e1b43417120a31f0403baf05d5e66`, alongside the source MMK/N0 functions.
MMK (MetaMasterKernel) names the common semantic plane. N0 names a situated
coordination function; it is orthogonal to that plane and to the host identity.

| Function | Published baseline | Candidate incarnation |
| --- | --- | --- |
| Common orientation, KA/FDLA, competence formation and learning | Present in the semantic core and competence field | Preserved and exercised inside the coordination method |
| Intent-preserving delegation | Faculty declared; entry led to the generic composition protocol | Existing faculty now reaches `maios-project-coordination`, which teaches handoff, direct responsibility and integration |
| N0 overview and return | Open fronts and causal margin exist; generic delegation entry omits the method | Recover useful fronts, retain sources and uncertainty, delegate the object with cognitive freedom, reconcile effects and learning |
| Another harness uses shared competences | Adapter instructions and host adaptation exist | Reach the actual living bodies, distinguish native discovery from reading, preserve local identity and form the needed connection |
| Per-instance capability state and simultaneous writes | One selected adapter; no general concurrent-writer lock | Competence recognizes this boundary and can evolve the affected owners from a real case; no runtime or synchronization change in this candidate |

The private MMK/N0 controller, historical schemas and node topology are not
transferred wholesale. Their useful functions become project-native knowledge;
their former forms do not prescribe every future project or cognitive path.
Having the same files does not establish the same identity, capabilities or
behavior. Several instances can share source-bound method while retaining
their own local cores, context and intentional specialization.

## Operative entry

Use [project coordination](../skills/maios-project-coordination/SKILL.md) when
handoff, direct coordination or returned contributions matter. It reaches
[host adaptation](../skills/maios-project-host-adaptation/SKILL.md) and its
[shared-project method](../skills/maios-project-host-adaptation/references/shared-project-continuity.md)
when a receiving harness needs a connection. Ordinary single-instance work
continues without a coordination stage. These entry relations remain open to
other circumstances and newly formed competences.

The installed `compose` command can expose the existing delegation faculty for
`instance_handoff`, `shared_project_continuation` or `direct_coordination`.
These are recall hints, not prerequisites for using the method. The installed
entry and supporting knowledge are included by the canonical release projection.
Package verification can establish their presence and navigability; an actual
receiving model's use and later assimilation require evidence from that work.

The current scope is the competence and its reachable package incarnation.
Creating profiles, configuring OpenCode/Claude Code/Hermes in an operator's
workspace, changing structured host state or introducing a coordination service
belongs to a subsequent concrete case.
