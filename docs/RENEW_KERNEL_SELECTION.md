# Production maintenance: renew the method selection

This procedure is for maintainers with access to the private production compiler.
It is not required to install, use, or rebuild the included distribution.
Public contributors start with [the public build path](GENERATED_KERNEL_BUILD.md).

The source competence owns this repeatable production movement. Begin with the
meaning to transfer and the native competences that must act differently.
The system, context, formation and knowledge-continuity bodies already own
contextual understanding, learning and reentry; do not copy another consumer's
configuration or an entire neutral generated tree into this product.

Consolidate the desired method bodies in a source commit. Use a clean RepoKernel
checkout at the selected immutable compiler commit. RepoKernel is needed on the
production machine for renewal; normal builds and receiving projects use only
the retained plan and the Python standard library.

```text
python -B tools/renew_kernel_selection.py --source-commit <40-character-product-commit> --compiler-root <local-RepoKernel-checkout> --compiler-commit <40-character-compiler-commit> --review-date YYYY-MM-DD
python -B tools/build_release.py
python -B tools/verify_distribution.py
```

Renewal reads the projection and method bodies from Git blobs, even if the
current checkout contains later edits. It forms SourceManifest, ProjectModel
and SeedSpec, calls the actual compiler and checks the result with the native
consumer. It then writes `release/generated/` and writes
`release/GENERATED_KERNEL_SELECTION.json` last. A mismatched or interrupted
selection stops the ordinary builder before replacing the existing package.
Keep generated changes together in the following source commit. No historical
callback patch or experimental installation loop participates in this path.

The selected body corpus digest covers canonical source paths and normalized
body hashes. Source links identify the exact published Git blobs; the plan
retains their content. The builder's whole-source digest is a separate identity.
An unchanged renewal with the same commits and review date produces identical
inputs, plan and selection. Inspect the actual artifact difference, preserving
onboarding and native host entry, rather than treating a revision number as proof.

## Entity profile remains a qualified independent derivation

The retained `release/repokernel/` bundle still supplies historical role and
source-catalog inputs to `builder.composed_project_entry_profile()`. Its
9192fe6/dev0 provenance stays intact. The current product combines those inputs
with AUTONOMOUS_ENTRY_CONTRACT, the family contract and native competence paths.
For example, current entry policy supersedes the historical interview policy.
The new method plan does not claim to regenerate this retained entity input.

For 4.1.0 the delta concerns situated understanding and continuity in the native
methods. The resulting entity structure and its deferred-context contract remain
appropriate, so the historical bundle is retained. The distribution manifest
records that provenance separately from generated method selection. A later
functional change to an entity field must follow this active transformation;
mere equality of compiler revision labels is not a goal.

## Release and subsequent project updates

Retain the full acquisition path: instructions before installation, recognition
of project and host, missing requirements, preview and exact apply, then useful
work and evolving context in the project. A new release does not overwrite an
installed project's knowledge. The installed UPDATE_CONTINUITY method compares
the original baseline, local evolution and new upstream proposal; the installer
does not merge different versions. Do not turn source contact into an automatic
download or migration. Actual use can supply the next learning without a new
mandatory experiment before every release.
