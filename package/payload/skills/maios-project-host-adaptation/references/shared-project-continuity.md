# Continue The Same Project Through Another Harness

Use this knowledge when another assistant actually enters the project, the
operator wants to prepare that entry, or a handoff exposes an access or
continuity difference. Its purpose is to know how to form the needed setup at
that moment. It does not preinstall hosts, create profiles or activate sharing.

## Recover What Is Shared And What Is Situated

Establish the receiving harness, selected working root and real project owner
from the present environment. The same folder on one filesystem, another
checkout and a copy on another machine have different freshness and write
relations. A workspace container may hold several separately owned repositories.
Recover the relevant project's current source and causal margin before choosing
a write path; a previous assistant's active task need not be the current task.

Shared project knowledge includes the semantic core, competence and meta-skill
bodies, source references, accepted changes and the current work that must
continue. A harness may retain its own native entry, local kernel projection,
profile and situated memory. Keep those connected to their source without
cloning another actor's identity, credentials, private sessions or runtime
databases. Do not copy a complete application home to obtain a competence.

If a root instruction identifies another node or a specific application,
understand that binding before preparing the receiving entry. Preserve the
governing instruction hierarchy and form the smallest owner-selected native
bridge; do not impersonate the previous actor or silently rewrite shared boot
for every other harness. Host and model names do not determine a new permanent
folder topology. Separate cores can be projections of a shared method, and
intentional local differences remain attributable and revisable.

## Make The Needed Knowledge Reachable

Follow actual discovery from the harness entry to the living competence body
and its supporting files. Native skill metadata can point to a canonical body;
verify that the harness can read it and resolve the reference in its real
working directory. If a native system needs a copy, keep its source and refresh
relation explicit. Avoid two independently maintained copies of the method.
Load pertinent knowledge progressively; the whole catalogue need not be active.

Read `HOSTS.md` for the installed adapter and current owner documentation when
its mechanics need clarification. Examples of distinct discovery mechanisms:

- [OpenCode](https://opencode.ai/docs/skills/) supports project `.opencode/skills`
  and compatible `.agents/skills` or `.claude/skills` entries.
- [Claude Code](https://code.claude.com/docs/en/skills) supports project
  `.claude/skills`; source precedence can affect which same-named skill is used.
- [Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)
  has profile-owned skill storage; identify the active profile and its home.

These examples are refreshable mechanics, not an exhaustive host list. A folder
created for a different application may be readable without being automatically
discoverable. Direct reading can supply the method when supported; native
discovery and actual exercise remain distinct observations.

## Resume Before Extending Infrastructure

Recover the live object, intent and its source, last faithful result, ongoing
changes, next useful movement and invalidator. Read current files rather than
treating a transferred summary as current authority. Explain the contribution
of the pertinent competences through the work. If only continuity or discovery
was missing, that small connection can be sufficient to resume useful work.

Observe tools and capabilities in the receiving instance. Do not inherit a
network, write, delegation or maintained-reentry claim from another session,
even when both sessions use the same adapter. If the existing state can record
only one selected adapter, that describes its present implementation. Do not
rename the new host to fit it, overwrite the old host's observation or admit
an event that falsely attributes the new instance's capabilities.

Keep useful knowledge work at its actual owner when the receiving host can do
it. Preserve a compact, source-qualified pending observation or handoff where
structured state support is insufficient. A readable method is immediately
available; an unsupported structured transition is still unperformed. A later
capable instance reconciles that relation without repeating completed effects.

## Form A Larger Capability When The Case Requires It

If actual continued or simultaneous use needs per-instance state, let this
competence and `maios-project-coordination` derive the change from the case.
Separate common project state from instance identity, adapter, capabilities,
freshness and responsibility. Preserve existing observations and the recovery
of every affected owner. Follow a proposed change through admission, status,
composition, replay, receipts, derived context and installed entry consumers.
Current integrity checks must follow the revised owner relation rather than
freeze the former single-host representation.

Choose a local adapter, owner-state evolution, handoff mechanism or another
fitting form. Source-linked changes and error recovery are real requirements;
a fixed multi-host database, permanent coordinator or universal synchronization
service is not predetermined. Shared disk access alone does not coordinate
concurrent writes. Use the project's real collaboration mechanism and integrate
returned work without overwriting another actor's contribution.

Observe the next useful work and a fresh reentry at the level actually reached.
Do not equate installed instructions with obedience or a runtime check with
model assimilation. Let the result improve both the local connection and this
competence. Retire obsolete active routes while preserving the useful source
and reasons for future cases.
